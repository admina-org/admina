**Tech Stack:** Python 3.11, pytest (`.venv/bin/python -m pytest`). Branch `release/0.10.0`. Commit per task; NEVER tag; do not push.

**Audit findings closed here:** A (response dict PII leak), B (would_action never persisted → observe analytics dead), D (validate casing), E (validate ignores GOVERNANCE_MODE), F (validate PII runs after block), H-server (dict keys unscanned in governance.py helpers), K (guard contract errors swallowed). **Deferred to Plan 03b:** G (GovernedAgent per-call uuid4), H-sdk (governed_agent `_collect_strings`), I (GovernedModel default protection), J (GovernedData classifies locator). **Deliberately kept:** the `/api/v1/validate` `MODIFY` action string (external REST contract for n8n/CheshireCat/OpenClaw consumers) — its rename is a separate coordinated breaking change, NOT done here.

**Behavior-change ledger (append to 0.10.0-changelog-notes.md in the relevant task):** `/api/v1/validate` now honors `GOVERNANCE_MODE` (observe/dry-run no longer always-enforce); `/mcp` now redacts PII in dict-shaped tool results; observe-mode "would-have-blocked" events now persist and reach the dashboard suggestion engine.

## Self-review notes

- The canonical ORDER (loop→firewall→PII→guards) is already what `run_pipeline` does and what `/api/v1/validate` already does — so this plan introduces NO ordering change for the server surfaces. The GovernedAgent reorder (firewall→loop today) is an SDK concern → Plan 03b.
- `MODIFY` is deliberately preserved at the REST layer (external contract). If a future decision renames it to `REDACT`, that is a coordinated breaking change touching the n8n node + CheshireCat + OpenClaw + their tests + a CHANGELOG breaking-note — explicitly NOT in this plan.
- Killing `MODIFY` was listed in the spec's D2; this plan downgrades that to "keep, deferred" because the spec did not account for the external-consumer breakage. Flag for the user at release time.
- Plan 03b (SDK half) covers: GovernedModel default full protection (opt-out flags), GovernedAgent stable session_id + dict-key scan in its own `_collect_strings`, GovernedData content (not locator) classification, and unifying the SDK pipelines onto `run_pipeline` where it fits.
