# 0.10.0 Plan 04 — D6: Forensic Chain Integrity (CRITICAL + HIGH)

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Stop the forensic store from silently resetting/forking the hash chain when the state file is lost or corrupt (audit CRITICAL), make `verify_chain` detect tail truncation (audit HIGH), and serialize concurrent writes so the chain can't fork — then wire verification into a real path (`admina doctor` + a REST endpoint).

**Architecture:** Two stores share the bug class: `ForensicBlackBox` (`admina/domains/compliance/forensic.py`, the proxy's production store for memory/filesystem/s3) and the plugin `FilesystemForensicStore` (`admina/plugins/builtin/forensic/filesystem.py`). Both restore `chain_head`/`record_count` ONLY from a mutable state file; if it's missing/corrupt they silently fall back to GENESIS/0 and the next write restarts the chain — the plugin OVERWRITES record files (flat `{count:08d}.json`), ForensicBlackBox FORKS (date-partitioned, duplicate sequence numbers). The fix: reconstruct chain state from the actual stored records; never trust a missing state file over existing records; serialize writes; and make `verify_chain` cross-check the on-disk record set against the persisted `record_count`/`chain_head`.

**Tech Stack:** Python 3.11, pytest (`.venv/bin/python -m pytest`). Branch `release/0.10.0`. Commit per task; NEVER tag; do not push.

**Audit findings closed:** CRITICAL `forensic/filesystem.py:77` (silent chain reset/overwrite on missing/corrupt state) + the same class in `ForensicBlackBox`; HIGH `forensic/filesystem.py:99` (verify_chain blind to tail truncation) + the same in `ForensicBlackBox.verify_chain`; the D6 lock/concurrency item.

**Behavior-change ledger:** the forensic store now reconstructs its chain state from stored records (a missing/corrupt state file no longer silently restarts the chain); `verify_chain` now fails when records are missing relative to the recorded count or the chain head doesn't match the last stored record; concurrent writes are serialized; `admina doctor` and `GET /api/v1/forensic/verify` report chain integrity.

**Test note:** the existing forensic tests are the regression net — locate them first: `grep -rln "ForensicBlackBox\|FilesystemForensicStore\|verify_chain\|_restore_chain" tests/ | grep -v __pycache__` (expected: `tests/test_forensic_blackbox.py` and a plugin test). Do NOT weaken any tamper-detection test.

```python
    def _reconstruct_chain_state_from_records(self) -> bool:
        """Rebuild chain_head/record_count from stored records.

        Returns True if any record was found. Used when the mutable state
        file is missing or corrupt so the chain is never silently restarted
        from GENESIS while records exist.
        """
        records = self._read_back_records()
        if not records:
            return False
        last = records[-1]  # _read_back_records sorts by sequence_number
        self.record_count = last.get("sequence_number", len(records))
        self.chain_head = last.get("record_hash", "GENESIS")
        logger.warning(

            "(state file missing or corrupt): seq=%d, head=%s...",
            len(records), self.record_count, self.chain_head[:16],
        )
        return True
```

### Task 2: ForensicBlackBox — serialize writes (concurrency fork)

`record()` (forensic.py:205-236) does an unlocked `record_count += 1` → build → `_store_to_s3` → `_persist_chain_state`. Two concurrent calls read the same count and fork the chain. `record()` is synchronous (proxy calls it directly), so a `threading.Lock` is the right primitive.

**Files:** `admina/domains/compliance/forensic.py`; Test.

- [ ] **Step 1 (failing test):** prove concurrent records produce a contiguous, non-forked chain:

```python
def test_forensic_concurrent_records_do_not_fork(tmp_path):
    import threading
    from admina.domains.compliance.forensic import ForensicBlackBox

    fb = ForensicBlackBox(filesystem_dir=str(tmp_path))

    def _w(i):
        fb.record({"event": f"e{i}"})

    threads = [threading.Thread(target=_w, args=(i,)) for i in range(20)]
    for t in threads: t.start()
    for t in threads: t.join()

    assert fb.record_count == 20
    res = __import__("asyncio").run(fb.verify_chain())
    assert res["valid"] is True
    assert res["records"] == 20   # 20 distinct sequence numbers, no duplicates/forks
```

Run → FAIL (forked/duplicate sequences; record_count < 20 or verify invalid).

- [ ] **Step 2 (implement):** add `self._write_lock = threading.Lock()` in `__init__` (import `threading`). Wrap the body of `record()` in `with self._write_lock:` so the increment + store + persist are atomic. Keep the return outside or inside consistently (return the computed result).

**Files:** `admina/domains/compliance/forensic.py`; Test.

```python
        result = self.verify_records(records)
        valid = result["valid"]
        if last_n == 0:

            # tail (records removed after the last seen one) is detected — the
```

## Self-review notes

- The fix treats the immutable RECORD chain as the source of truth and the mutable state file as a cache — a missing/corrupt cache is reconstructed from records, never used to silently restart the chain. This is the correct tamper-evidence posture (records are append-only / WORM-locked on S3; the state file is explicitly mutable per the existing comment).
- `verify_chain` anchoring catches *naive* truncation (records removed, state untouched). A sophisticated attacker who also rewrites the mutable state file to match a truncation is out of scope for this fix — defending that requires anchoring the state file itself (e.g. signing it), which is a larger change; note it as a follow-up. The S3 WORM Object Lock already defends the record objects against deletion on that backend.
- ForensicBlackBox.record() is sync → `threading.Lock`; the plugin append() is async → `asyncio.Lock`. Do not mix them.
- The in-memory backend must keep `verify_chain` → valid:true (no durable records to verify); the anchoring logic is gated on a durable backend being configured.
- Concurrency: with the write lock, `record_count`/`chain_head` mutations are atomic; the date-partitioned S3/filesystem keys plus contiguous sequence numbers mean `_read_back_records` sorts deterministically.
