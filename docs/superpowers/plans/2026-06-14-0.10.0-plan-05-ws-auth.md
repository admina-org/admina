# 0.10.0 Plan 05 — WebSocket & Auth Unification (single-tenant)

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Fix the live WebSocket cookie-auth regression and the unreachable signed-cookie path in the API-key auth provider, by unifying HTTP + WS + provider auth onto one resolver; add an Origin allow-list on the WS upgrade (anti-CSWSH); and pin the fail-closed default with a test + loud startup warning.

**Architecture:** Today three places authenticate independently and have drifted: the HTTP `auth_middleware` (correct — checks raw key OR `_verify_dashboard_token(cookie)`), the WebSocket `/live` endpoint (BROKEN — `compare_digest(cookie, raw_key)`), and `APIKeyAuthProvider._extract_key`/`authenticate` (BROKEN — returns the cookie as the "key", compared raw). Extract one shared resolver `verify_credential(headers, query_params, cookies, settings) -> bool` (raw key via header/Bearer/query OR signed-cookie token) and route all three through it. The WS endpoint needs the resolver injected into `create_dashboard_endpoints` (it currently only receives `get_settings`).

**Tech Stack:** Python 3.11, pytest (`.venv/bin/python -m pytest`). Branch `release/0.10.0`. Commit per task; NEVER tag; do not push.

**Audit findings closed:** HIGH `dashboard.py:232` (WS cookie vs raw key), HIGH `apikey.py:137` (signed cookie rejected by the provider path → `_verify_dashboard_token` unreachable when a provider is loaded), and the WS Origin/CSWSH gap. The HIGH `proxy/main.py` "fail-open default" finding is **verified already-closed** (ALLOW_UNAUTHENTICATED defaults False); Task 5 pins it with a regression test rather than assuming.

**Scope decision (deviation from brainstorm, flagged):** the approved "one coarse scope (read/full) in the signed cookie" is DEFERRED — with a single `ADMINA_API_KEY` there is no mechanism to issue a read-only cookie (every cookie derives from the master key), so the scope field would be inert plumbing in 0.10. It becomes meaningful only with the multi-key model (0.12). Tracked in the carry-forward; not built here.

**Behavior-change ledger:** the bundled browser dashboard's live WebSocket feed now authenticates via the signed session cookie (was broken when a key was set); the API-key auth provider now accepts the signed dashboard cookie; the WS upgrade now rejects disallowed Origins; HTTP/WS/provider auth share one verifier.

```python
def verify_credential(
    *,
    headers: dict | None = None,
    query_params: dict | None = None,
    cookies: dict | None = None,
) -> bool:
    """Authenticate a request from its credential parts (header/query/cookie).

    Accepts the raw ``ADMINA_API_KEY`` via ``X-API-Key`` / ``Authorization:
    Bearer`` / ``?api_key=`` (constant-time compare), OR the signed
    ``admina_session`` dashboard cookie (verified, never the raw key).
    The single source of truth shared by the HTTP middleware, the WebSocket
    upgrade, and the API-key auth provider so they cannot drift.
    """
    headers = headers or {}
    query_params = query_params or {}
    cookies = cookies or {}
    if not settings.ADMINA_API_KEY:
        return False
    raw = (
        headers.get("X-API-Key")
        or headers.get("x-api-key")
        or headers.get("Authorization", headers.get("authorization", "")).removeprefix("Bearer ").strip()
        or query_params.get("api_key")
        or ""
    )
    if raw and _secrets.compare_digest(raw, settings.ADMINA_API_KEY):
        return True
    return _verify_dashboard_token(cookies.get(_DASHBOARD_COOKIE, ""))
```

### Task 4: Origin allow-list on the WebSocket upgrade (anti-CSWSH)

## Self-review notes

- The shared `verify_credential` is the single source of truth; HTTP middleware, WS upgrade, and the apikey provider all route through equivalent logic. The apikey provider replicates the ~8-line HMAC verify locally (NOT importing proxy) to respect layering — accept the small duplication over a layering violation.
- Origin check: absent Origin ⇒ allowed-with-credential (non-browser clients like the n8n node send no Origin and rely on `?api_key=`/header). Present-but-disallowed ⇒ rejected. `*` in CORS_ORIGINS ⇒ allow any (operator opted in).
- Deferred (carry-forward): the coarse read/full scope in the cookie token — inert in 0.10 (single key, all cookies derive from the master key; no read-only issuance path). Meaningful only with multi-key (0.12). Adding it now would be speculative plumbing.
- The fail-open finding is treated as verify-and-pin (the default is already fail-closed); if Task 5 Step 1 reveals an actual gap, that becomes a real fix.
- `?api_key=` in the query string leaks the raw key into logs/history — kept for header-less browser WS compatibility but documented as the less-preferred path; the cookie is the preferred browser credential.
